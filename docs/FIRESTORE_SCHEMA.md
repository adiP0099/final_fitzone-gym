# Firestore schema and access policy

This document describes the Firestore schema and the client workflows implemented in the current phase. Creating this document or deploying the rules does not create collections or records.

All collection documents use Firestore document IDs, not client-chosen identity claims. A user's `users/{uid}` document ID and `uid` field are the Firebase Authentication UID. References to users use that UID; references to plans, trainers, memberships, bookings, and payments use their Firestore document IDs. The rules do not authorize a user based on a `role` value stored in a user-editable document.

Timestamps below are Firestore `Timestamp` values. `createdAt` and `updatedAt` should be written with server timestamps. Money uses integer minor units (for example, cents) plus an ISO 4217 currency code; do not store floating-point currency values.

## Roles and initial admin provisioning

New registrations remain ordinary members. A registration form, URL, local storage value, Firestore `users/{uid}.role`, or client-side state must never grant admin access.

The rules authorize admins only when the verified Firebase Authentication ID token contains the custom claim `role: "admin"`. Custom claims must be set using the Firebase Admin SDK in a trusted environment, never in the browser. The `role` profile field is descriptive only; the rules never use it to authorize access.

For an initial administrator, an authorized project owner should:

1. Confirm the exact existing Firebase Authentication account UID through the Firebase Console.
2. Run an explicitly reviewed Admin SDK operation in a secured administrative environment, using Application Default Credentials or another secret-management method. Do not put a service-account key in this repository, Vite variables, or browser code.
3. Set the custom claim only for the reviewed UID, for example with the trusted Admin SDK operation `getAuth().setCustomUserClaims(uid, { role: 'admin' })`. This operation replaces the user's existing custom-claims object; inspect and preserve any separately approved claims when constructing the replacement.
4. Have that user refresh their ID token (sign out and back in if necessary), then verify the claim and deployed rules with rule tests before using admin access.

No account is promoted by this phase. No custom claims are issued by the frontend. The local provisioning procedure is documented in [`ADMIN_CLAIM_PROVISIONING.md`](./ADMIN_CLAIM_PROVISIONING.md), but live admin access is not usable until an authorized operator provisions a claim and the reviewed rules are deployed. Admin SDK/server operations bypass Firestore Security Rules and must independently validate authorization and data.

## Rule boundaries and limitations

Rules are in [`../client/firestore.rules`](../client/firestore.rules). They use `request.auth.uid` to establish ownership and an Auth custom claim for admin access. User-created profile fields cannot assign an admin claim. Unmatched paths are explicitly denied.

Members cannot create or change memberships directly. The membership request workflow uses a member-owned request and an authenticated administrator's Firestore transaction. The rules require the request to move from `pending_review` to `approved` in the same atomic commit that creates one matching `active` membership, validate the member, plan, request, and dates, and require `paymentStatus: "unpaid"`. A rejected request cannot create a membership; request decisions are single-use. The request document ID is the plan ID, so Security Rules prevent duplicate requests for the same member and plan, even if requests are submitted concurrently. The current flow permits one request per member-plan pair; a rejected request cannot be resubmitted.

All direct writes to attendance and payments remain denied because check-in and payment confirmation require trusted validation. Enquiry creation is also denied until a trusted submission workflow is designed. Booking writes are admin-claim-only until capacity and scheduling checks can be performed safely. Other admin dashboard pages remain demos; membership requests are the implemented Firestore-backed admin workflow.

This client-only transaction design uses Firebase Authentication custom claims and Firestore Security Rules and does not require Cloud Functions or a Blaze upgrade. Live use still requires the reviewed rules to be deployed and a real administrator custom claim to be provisioned through the documented trusted local Admin SDK process. Emulator claims do not provision a live account.

The rules are not deployed. They have been runtime-tested against the local Firestore Emulator using `npm run test:rules` and the dedicated non-production project ID `demo-fitzone-rules`. This does not verify the live Firebase project or constitute deployment approval. Query clients must constrain member record queries to their own `memberUid`; Firestore rules are not filters and reject a query that could return another member's records. Active-plan/trainer listing queries must constrain results to `active == true` unless the caller has the admin custom claim.

The rules validate the type and maximum count of the `benefits` and `specializations` lists, but do not inspect the type of each list item; they validate `availability` as a map and cap its key count, but do not validate its nested shape. Writes to these collections require the trusted admin claim, but any future admin UI or trusted writer must still validate list items and availability structure before writing.

## Shared client service layer

Reusable service factories are in `client/src/services/firestore/`, and `client/src/services/firestore/index.js` exports configured instances using the existing `auth` and `db` from `client/src/firebase/config.js`. The factories accept Auth/Firestore dependencies so they can be exercised against the local emulator. Member plans, requests, memberships, and the admin request review page use these services; unrelated admin dashboard pages remain demo-only.

Member read methods derive ownership from `auth.currentUser.uid`. Membership request creation derives the UID from Auth, snapshots the active plan, and uses server timestamps. Admin review first checks the verified ID token's custom claim and performs an atomic transaction subject to the Firestore Rules checks above. Service read methods return `{ data, empty }`; listener methods emit `{ loading, data, empty, error }`. Methods for direct membership, member booking, attendance, enquiry submission, and payment writes remain unavailable instead of bypassing rules.
